# Lot 2 — sauvegarde et documents privés

Cette pièce décrit le code proposé ; les résultats réellement exécutés figurent dans `GENERATOR_REVIEW.md` et les sorties du banc. La migration additionnelle est `supabase/migrations/20260917172412_izord_generator_versions.sql`. Les migrations auditées du lot 1 restent intactes.

## Modèle et opérations

`lib/izord/repository.ts` utilise le client Auth existant, les tables `izord_projects`, `izord_project_versions`, `izord_assets`, les affectations et la matrice du lot 1. Aucun payload OAR n'est utilisé. Un enregistrement explicite porte la révision attendue ; `izord_save_generator` appelle l'enregistrement atomique existant et conserve son contrôle d'auteur Auth, de statut et de concurrence. Une référence étrangère/non finalisée fait échouer la transaction entière. Un conflit ou une réponse après changement de compte/annulation ne retourne pas un état « enregistré ». Le brouillon de l'appelant n'est pas modifié. Une transaction déjà reçue peut cependant avoir été validée par le serveur avant l'annulation : recharger la liste après reconnexion permet de retrouver son état réel.

Le payload `IZORD_GENERATOR_V1` contient `data` (forme compatible avec `ProjectData`, photographies remplacées par identifiants privés) et `sourceDocuments`. Les bytes des images et PDF ne figurent pas dans le JSON de la base. `izord_generator_asset_refs` associe chaque emplacement photo, galerie ou PDF à la révision enregistrée. Les fichiers finalisés peuvent être référencés par plusieurs révisions du même projet, sans duplication des bytes ni modification de leur identité. Les nouvelles révisions sont des snapshots immuables du payload. Les identifiants, auteurs et approbations d'un JSON importé ne sont jamais repris comme autorisations.

Le lecteur garde la matrice du lot 1 : texte d'un dossier affecté, sans téléchargement des photographies ni PDF source ; seules les présentations finalisées explicitement autorisées sont téléchargeables. Il ne peut enregistrer, transférer ou approuver. Un contributeur peut éditer ses dossiers et ceux affectés, mais ne peut approuver ou publier un téléchargement lecteur. Admin/associé gardent leurs pouvoirs existants. Le statut approuvé interdit encore l'ajout/finalisation documentaire : un responsable doit créer une révision non approuvée avant de nouvelles pièces. Cette limite n'a pas été contournée pour le générateur.

## Transferts et résidus

Le transfert est direct du navigateur vers Storage, via une URL signée limitée à un nouveau chemin UUID, sans upsert. `XMLHttpRequest` fournit la progression, une interruption et une limite de deux minutes ; les bytes ne transitent ni par une route Next/Vercel ni par le JSON CRM. Le fichier est limité à 25 000 000 octets côté pilote ; le bucket conserve son plafond de 26 214 400 octets du lot 1. Le nouveau trigger de finalisation compare le nombre d'octets effectivement enregistré dans les métadonnées Storage et le MIME reçus aux valeurs annoncées, même si le RPC historique de finalisation est appelé directement. La signature locale du fichier est également vérifiée avant envoi. Cela ne constitue pas un antivirus ou une reconnaissance exhaustive du contenu ; aucun hachage serveur du contenu binaire n'est calculé. L'identité/version de l'objet Storage est figée par le cycle documentaire R1.

Une capacité d'upload déjà signée reste utilisable jusqu'à son expiration (deux heures dans la version testée). Une révocation n'annule pas cette capacité : un dépôt pending peut donc encore arriver. Lecture, nouvelle inscription d'asset, sauvegarde et finalisation exigent les droits actuels ; la finalisation est refusée après révocation. Après finalisation ou retrait, le trigger R1 interdit remplacement, suppression puis réimport et upsert signé au même chemin. Une nouvelle présentation possède une nouvelle identité et `reader_download=false` ; aucune publication n'est héritée.

Les interruptions laissent un asset `pending`, visible à son auteur autorisé tant que sa révision est courante. L'interface propose un abandon explicite : `izord_withdraw_asset` crée le retrait logique définitif, bloque la finalisation, les lectures et toute réutilisation du chemin. Pour reprendre, sélectionner à nouveau le fichier crée un nouvel asset ; il n'y a pas de reprise partielle TUS. Le choix du transfert simple a pour limite de retransférer entièrement un gros fichier interrompu ; la documentation Supabase conseille TUS au-delà de 6 Mo pour améliorer cette reprise.

Si une autre révision a été créée entre-temps, ou si des uploads ont été finalisés avant un conflit de sauvegarde, l'auteur contributeur ne dispose pas d'un droit de retrait supplémentaire : un admin/associé peut retirer ces résidus avec le RPC existant. Le retrait n'efface jamais physiquement les bytes ni les tombstones. Les pending d’ancienne révision ne sont pas listés par la RLS utilisateur actuelle : leur découverte exige un inventaire administratif local, pas le seul bouton « Vérifier les transferts ». La procédure locale consiste à relever les IDs pending ou finalisés sans références de version, vérifier leur projet/révision et les références, puis retirer explicitement les seuls résidus choisis. Le banc vérifie les retraits pending, le cas d'une ancienne révision, et le refus de réutilisation ; les volumes sont conservés. Aucun nettoyage automatique, suppression d'objet finalisé/référencé ou tâche distante n'est ajouté.

La galerie est chargée en mémoire depuis les objets privés accessibles, pas stockée dans localStorage/IndexedDB. Le renouvellement Auth seul ne lance aucune sauvegarde. Les méthodes recontrôlent le compte avant et après les opérations asynchrones et l'interface annule les opérations lorsqu'elle change de dossier/compte. Un export archivé utilise la révision exactement confirmée ; si une autre révision est observée après son accusé, le pilote signale un conflit au lieu d'étiqueter le brouillon avec cette révision tierce.

Le lot 2 ajoute un budget agrégé de 100 000 000 octets de photographies distinctes par dossier, en plus des limites par fichier/dimensions. JSON, ajout manuel, recadrage, application PDF et sauvegarde le contrôlent avant de retenir le nouveau projet. L'hydratation Storage vérifie d'abord les tailles déclarées connues, puis cumule les octets effectivement reçus avant leur conversion/accumulation base64 ; un ancien asset sans taille déclarée est contrôlé à réception. Une seule réponse déjà en cours peut donc être reçue avant ce refus. Les occurrences répétées comptent séparément dans une seconde limite de 170 000 000 caractères JPEG incorporés, conservant une marge dans le JSON maximal de 180 Mo : plusieurs références au même gros objet ne peuvent provoquer un export JSON de plusieurs gigaoctets. Les gardes testent les tailles sans allouer ces volumes. Ces plafonds n'assurent pas qu'un appareil disposant de très peu de mémoire pourra ouvrir tous les dossiers admissibles.
